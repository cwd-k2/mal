# D097. external opaque carrierをStorableにする

- Status: Accepted
- Date: 2026-10-03
- Scope: language、frontend、reference LLVM backend
- Refines: D075、D096

## 問題

external opaque valueはpublic C ABIを通るpointer-widthのcopyable carrierを持ち、Mal側のShareやDropを必要としない。一方、canonical
memory representationは持たず、従来のBuffer loweringはcanonical storageまたはmanaged callback付きstorageの二択だった。このため
`Buffer<Handle>`をfrontendで認めるだけではbackendがelement storageを選べなかった。

Poolだけがexternal handleを保存できる形にするとBufferとPoolに異なる`Storable`が生じる。逆にexternal resourceのcloseやreferent
lifetimeをBufferへ暗黙に持ち込むと、external contractが所有するauthorityをMalのplace lifecycleと混同する。

## 決定

external opaque typeを`Storable`に加える。Bufferへの格納、read、replace、relocation、終了はcarrier bitsについてshallowに行い、host
referentのlifetimeを延長せず、closeその他のresource operationを暗黙に実行しない。`Representable`と`HostMappable`は変更しないため、
external opaque elementを`from`、`into`、canonical memory helperへ渡せない。

LLVM Buffer storageを次の直交した分類にする。

```text
ElementStorage(T) = Canonical(layout)
                  | Runtime(layout, Lifecycle(T))

Lifecycle(T) = Trivial
             | Owned
```

external opaque carrierは`Runtime(_, Trivial)`となり、LLVM runtime value layoutでload/storeするが、C runtimeはplain Buffer entry pointを
使い、retain/release callbackを生成しない。`Symbol`とBuffer handleを含むcarrierは`Runtime(_, Owned)`のままである。

## 理由

- placeが必要とするのはcarrier lifecycleを完結できることであり、canonical host memory representationではない。
- external carrierの通常のlocal copyとBuffer element copyに異なるresource authorityを与えない。
- representationとlifecycleを分けることで、canonicalだがTrivial、runtimeだがTrivial、runtimeかつOwnedを同じ分類から導ける。
- Pool導入前にBufferの`new`、`get`、`put`、`fill`、`copy`とgrowthを通し、Pool固有state machineから独立して境界を検証できる。

## 帰結

- genericな`Buffer<A>`が要求する`Storable(A)`はconcreteなexternal opaque typeについて満たされる。
- external opaqueを含むproductとsumも、他のfieldがStorableなら同じruntime-trivial storageへ置ける。
- functionとempty sumは引き続きStorableでない。
- callback収集はruntime representationではなくOwned lifecycleだけを対象にする。
- Pool handleを追加するときは新しいstorage categoryを作らず、このrepresentation/lifecycle分解を使う。
