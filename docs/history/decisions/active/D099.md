# D099. C host surfaceを型、定数、演算子、Call APIへ分ける

- Status: Accepted
- Date: 2026-10-06
- Scope: C ABI、reference compiler、runtime、documentation
- Refines: D035、D098

## 決定

C host surfaceを型マクロ、定数、context-freeな演算子、`mal_call_t *call`を先頭に取るCall APIへ分ける。型マクロは
`mal_type`、`mal_product`、`mal_sum`、`mal_owned`、定数は`mal_false`、`mal_true`、`mal_unit`とする。型query、opaque
carrier変換、lifecycleは演算子とし、`mal_storageof`、`mal_from_bits`、`mal_to_bits`、`mal_share`、`mal_move`、`mal_drop`を
`call`なしで使う。

runtime capability、Symbol構築、すべてのBuffer operationはCall APIとする。現在allocationやtrapを行わない観測や縮小も含め、
`mal_allocate`、`mal_deallocate`、`mal_trap`、`mal_symbol`、`mal_snapshot`、`mal_buffer`、`mal_data`、`mal_count`、
`mal_push`、`mal_replace`、`mal_fill`、`mal_copy`、`mal_append`、`mal_extend`、`mal_truncate`、`mal_reserve`は有効な`call`を
常に先頭に取る。

Share callbackとowner retainはcontext-freeにする。Shareはallocationせず、有効なresponsibilityに対して失敗しない。
representation固有のreference count overflowはpublicなcall capabilityを要求するfailureにせず、context-freeなinternal fatal
failureとして扱う。ABIを`0x000b00`へ上げ、旧名と旧signatureのcompatibility aliasは残さない。

## 理由

旧surfaceでは`call`の要否を知るために、各operationが現在allocation、trap、retainのどれを内部で行うかまで知る必要があった。
特にBufferの観測と縮小だけが`call`を取らず、同じruntime-managed valueのoperationから外れていた。Call APIをactivationへの所属で
分類すれば、内部effectの変化に依存せずsignatureを予測できる。

Share、Move、Dropは一つのresponsibility語彙であり、Shareだけに`call`を要求する根拠はbyte ownerのoverflow処理というrepresentation
detailだった。これをlifecycleのpublic contractに持ち込まず、三つをcontext-freeな演算子として揃える。`mal_storageof`は
`sizeof`や`_Alignof`と同じtype query、`mal_to_bits`は入力をconsumeしない変換であることを名前で示す。

## 帰結

- public carrier type formは`mal_type(Name)`、それらから再帰的に作る`mal_product`と`mal_sum`に限る。
- `mal_owned`はnamed managed typeだけを受け、任意のC型をowned carrierへ変える形式ではない。
- raw allocationの確保と解放は同じくactiveなcall activation内で行う。
- Bufferの単純な観測でも`mal_data(call, buffer)`と`mal_count(call, buffer)`を使う。
- public surfaceの一覧とCall APIの系統は[C host value API](../../../spec/c-host-api.md)を正とする。
