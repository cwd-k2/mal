# D093. 本体が型parameterに求めるkindをspecializationで検査する

- Status: Accepted
- Date: 2026-10-01
- Scope: generic本体の型検査とspecialization
- Refines: D086

## 問題

kindはsignatureだけから推論するため、constructorの引数としてだけ現れる型parameterはkind多相になる。一方、本体はその
parameterを、kind `Type`を要求する別のgeneric bindingへ渡せる。`peek<F, M, V> :: (F<M, V>, USize) -> [Unit, V]`を
`isLive<F, M, V> :: (F<M, V>, USize) -> Bool`の本体から呼ぶと、`isLive`の`V`はkind多相だが`peek`は`V`にkind `Type`を求める。
sourceにはkind annotationがないため、利用者はsignatureでこのkindを固定できず、こうした関数を書く手段がなかった。

## 決定

本体のtype applicationがenclosing bindingの型parameterのkind変数について得たkind等式を、bindingのkind requirementとして
保持する。本体の検査ではkind変数を書き換えず、specializationで型argumentがconcreteになった時点で等式を検査する。満たさない
instanceは、等式を生んだ本体のapplicationを示すcompile-time errorにする。規則は[parametric polymorphism](../../../spec/generics.md)に置く。

## 理由

- operation requirementと`Storable` requirementも、本体が求める条件をrequirementとして持ち、型argumentが具体化した時点で
  検査している。kindの条件も同じ扱いにすると、generic本体を一度だけ検査する構造を変えずに済む。
- concreteな型argumentのkindは常に具体的に決まるため、検査は一次のkind unificationで終わる。
- signatureから決まらないkindを`Type`とみなす既定値は、phantom parameterをkind多相にした[D092](D092.md)と食い違い、
  constructorを渡す使い方を理由なく閉ざす。拒否すると、具体化すれば常に整合するprogramを書けない。
