# D086. kind推論によるhigher-kinded constructorを採択する

- Status: Accepted; inference of kind-polymorphic phantom arguments refined by D092; body kind requirements refined by D093; implementation key patterns refined by D094
- Date: 2026-09-29
- Scope: language, compiler, and editor tooling

## 問題

generic algorithmを`Buffer`、user-defined product constructor、opaque constructorへ共通化するには、通常型だけでなく
type constructorをparameterへ渡す必要がある。kind annotationやtype lambdaをsourceへ追加すると、利用者が型level calculusを
直接管理する範囲が広がる。constructorをoperand shapeから逆算するとhigher-order unificationになり、局所型推論とcoherenceが不安定になる。

## 決定

declaration binderをtype-level abstraction、既存のtype applicationをapplicationとして扱い、compilerがprincipal kindを推論する。
partial applicationを認め、transparent aliasはbeta/etaを含むcanonical termへ正規化する。sourceへkind annotation、type lambda、placeholderを
追加しない。constructor argumentは明示prefixとして与え、kind `Type`の残りのargumentだけを従来の局所solverで推論する。

operation familyのconstructor-kind implementation keyはclosed canonical constructor termに限定する。specialization keyにはclosed
constructor termを含められるが、specialization後はkindとconstructor termを消去し、core以降の単相境界を維持する。

## 理由

利用者から見た構文を既存のgeneric declarationとapplicationへ保ったまま、constructorに共通するcodeを表現できる。rigid constructor
argumentとclosed operation keyによりhigher-order unificationを避け、既存のnon-overlap、termination、whole-program specializationを
first-orderな検査として維持できる。

現在の規則は[kindとtype constructor](../../../spec/type-constructors.md)、
[parametric polymorphism](../../../spec/generics.md)、[operation family](../../../spec/operation-families.md)を正とする。
