# D083. 保持するnative parameterへowned responsibilityを渡す

- Status: Accepted
- Date: 2026-09-28
- Scope: target layout非依存のexecution ownership planningとnative call ABI
- Refines: D055, D058

## 問題

D055は通常のnative callでcallerがmanaged argumentをcall中保持し、calleeがresult、capture、または保持するcalleeへの転送によって
parameterを渡す場合はcallee入口で`Share`するとした。callerがcall後にargumentを使わない場合、この`Share`とcaller側の`Drop`は
同じresponsibilityの移譲をretainとreleaseで表す。managed valueをloop stateとして返すcombinatorでは、この対が反復ごとに残る。

一つのcall siteから複数のfirst-class functionへ到達できるため、callee単体でABIを選ぶと同じcall siteが異なるparameter conventionを
要求する。recursive region、process entry、region machineryからのcallは、外側のauthorityとframe handoffを使う既存規則も維持する
必要がある。

## 決定

`execution/ownership`はapplication flow上で同じnative call siteを共有し得るfunctionをgroup化する。group内のいずれかがmanaged
parameterをreturn、capture、または保持するcalleeへのargumentとして使う場合、group全体のnative entryをowned conventionとする。
ただしrecursive region、process entry、frameまたはregion machineryが実行するcallに関わるgroupはborrowed conventionへ固定する。

owned call siteはargument responsibilityをcalleeへ渡す。callerが同じpathで後からargumentを必要とする場合は`Share`し、不要なら
`Consume`する。owned entryはliveなbinding parameterへ`ConsumeInto`し、保持しないparameterまたはwildcardを`Drop`する。
borrowed entry、region内handoff、self-tail handoffの既存規則はD055とD058に従う。

possible target、call mode、frame、region、parameter destinationを持つexecution stageがconventionを決める。LLVM backendはentryの
由来またはparameter livenessを再推論しない。reference count、last-use、選ばれたABIをsourceから観測可能にしない。

## 理由

calleeが保持する値には独立したresponsibilityが必要であり、callerが不要になったresponsibilityをそのまま渡す方が、入口で複製して
return後に元を終了するより直接的である。同じcall siteのtargetを一つのconventionへ閉じることでfirst-class dispatchのABIを保つ。

[loop combinatorの測定](../../performance/loop-combinators.md#2026-09-25--直接再帰との差と三つの規則)では、Bufferを返すloop stateで
owned convention導入前の1027M instructionsが377Mとなり、直接再帰の376Mと一致した。この差はsource semanticsを変えず、不要な
retain/releaseだけを除去した。

## 帰結

- ordinary mal wrapperも、result、capture、または保持するcalleeへparameterを渡すならowned native entryになり得る。
- 新しいowner-successor primitiveへparameterを保存するwrapperを同じ規則へ載せるには、そのprimitive effectを保持解析へ追加する。
- last-useのowned argumentはcallee内部のowner successorへ`Consume`できる。
- borrowed/pinnedな経路では同じ値を保持するために`Share`し、correctnessはconvention選択へ依存しない。
- runtime storageのreference countが1になることは保証しない。storage再利用は、移譲後にruntimeが一意性を確認するoptional techniqueである。
- target集合、owned/pinned group、caller use、callee entry effectをfocused ownership testで固定する。
