# D098. `extern`をruntime extension境界にする

- Status: Accepted
- Date: 2026-10-04
- Scope: language、C ABI、reference compiler、runtime
- Supersedes: D053、D054、D074
- Refines: D012、D015、D016、D031、D040、D052、D078、D084、D097

## 決定

`extern`のC implementationを、managed valueから隔離したhost adapterではなく、同じcompiler/runtime revisionへ結合するruntime
extensionとして扱う。別の`unsafe` declarationやsafe C ABIは設けない。generated headerはprogram固有のruntime carrierを公開し、
program非依存の`mal.h`はbuiltin carrier、call context、allocation、Buffer operation、型別lifecycle glueが使う共通operationを公開する。

external operationのparameterとresultには、functionを直接または再帰的に含まないclosed concrete typeを認める。`Symbol`、
`Buffer<A>`、managed memberを持つproductとsum、file-local opaque typeもC境界を通る。generic externとfunction callbackは、runtime
type descriptorとCからmalへ戻るprogram固有execution controlを導入しないため認めない。

managed parameterはhost body中のborrow、managed resultはhostからmalへのowned moveとする。hostが値をcall後も保持する場合は
型別shareで独立したresponsibilityを作り、後にdropする。Cは公開されたcarrier fieldとBuffer element storageを直接操作でき、helperを
迂回したcontract違反後の挙動は保証しない。extern callは未知のmemoryと外部stateを変更し得るeffectful operationである。

source-level `Address`、`from<A>`、`Buffer<A>.into`、`Representable`、canonical host memory layout、generated canonical memory helperを
削除する。Buffer elementはspecialization後のruntime carrier layoutで保存し、LLVM moduleとgenerated C headerが同じtarget layoutを
使う。C libraryやsystem callが必要とするpointerはC bodyがmanaged carrierからcall中だけ取得する。call後にも存在する外部memoryは
resource固有のexternal opaque typeまたはruntime-managed native objectへ閉じ込め、raw syscallと万能pointerをmal sourceへ公開しない。

ABIはcompiler/runtimeとのexact matchだけを保証する。generated artifactとhost sourceはcompiler更新後に再compileし、異なるABI
version間のsource compatibilityとbinary compatibilityを保証しない。

## 理由

同じprocessへ静的linkするCをAddress copy境界で隔離しても、host contract違反からmal programを保護できない。一方でこの境界は、
managed bytesを入出力するたびに外部allocation、Address、長さ、copy、release protocolを要求し、runtimeがすでに持つBuffer lifecycleを
C adapterが迂回する。

runtime carrierを直接共有すれば、allocationと回収はmal runtimeに残したまま、I/O、system call、codec、native collectionを
`Symbol`と`Buffer`へ接続できる。layout authorityはcompilerに残り、generated headerとstatic assertionがC viewを同じtarget planへ
一致させる。安全性を提供しない境界へ別のcanonical host representationを維持する理由はない。

generic implementationとfunction callbackを同時に開かないのは安全性の制限ではない。specialization後に消える型parameterをCへ
渡すdescriptorと、contextが保持しないcontinuationへCから戻るtrampolineが存在しないためである。未実装のexecution mechanismを
raw carrier公開から推測しない。

## 帰結

- `HostMappable`はlanguage judgmentではなくなり、extern surfaceはclosed concrete runtime carrierから生成する。
- `Storable`はBuffer placeのlifecycle条件として残り、external opaque carrierも引き続きstorableである。
- Engramのidentityとsource semanticsはmalが定めるが、extern CはvalidなEngramを構築、観測、変更できるTCBである。
- `Symbol`のimmutabilityなどruntime invariantをCが破った後のsource behaviorは保証しない。
- external opaque typeはone-word trivial carrierのまま維持し、resource lifecycleを暗黙にmanaged dropへ結合しない。
- dynamic plugin、cross-thread managed value、callback/reentry、新しいmanaged source typeは独立した後続判断とする。
