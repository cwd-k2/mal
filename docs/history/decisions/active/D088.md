# D088. opaque representation viewは片側だけに、operatorにも適用する

- Status: Accepted
- Date: 2026-09-29
- Scope: file-local opaque type、type checking

## 問題

宣言元fileのrepresentation viewは、比較の両側を宣言元fileのopaque層をすべて剥がしてから比べ、両側がopaque typeなら常に
不一致としていた。そのため`opaque B :: A;`では`B`を`Int32`とは比較できるのに、自身のrepresentationである`A`とは比較できなかった。
またprimitive operatorはoperandの型を構造的に調べたため、`#name`や`name # index`は通るのに、`count + 1i32`、`left == right`、
Symbolの`left + right`は宣言元fileでも拒否された。

## 決定

- 型の各位置では一方の側だけを、宣言元fileのopaque層を必要なだけ辿ったrepresentationとして見る。opaque typeは自身の
  representationの各層と一致し、同じrepresentationを持つ別々のopaque typeとは一致しない。
- 宣言元fileのprimitive operatorとnumeric literalは、operandと期待型をrepresentation viewで扱い、結果はrepresentationの型に
  なる。他のfileでは従来どおり適用できない。

規則は[型](../../../spec/types.md#file-local-opaque-type)に置く。

## 理由

- 「別々のopaque type同士をviewで変換しない」を保つには、同じ位置で両側を剥がすことだけを禁じればよい。片側を複数層剥がす
  ことは宣言元fileのauthorityの範囲内であり、`B`と`A`の比較を拒む理由にならない。
- 仕様は他のfileに対して「hidden representationによる構築、分解、operation適用はできない」と定めており、宣言元fileでは
  operation適用もviewの対象である。operatorだけを例外にすると`#`と`+`の間に説明できない差が残る。
