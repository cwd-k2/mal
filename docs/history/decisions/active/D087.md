# D087: 型項正規化のresource上限

- Status: Accepted (2026-09-29)

## 決定

reference compilerはcanonical type termの一回の正規化transactionを、256 nested term levelかつ65,536 normalization stepまで
受理する。超過は型検査が起点となったtype expressionのspan付きdiagnosticで拒否する。また、一つのdeclarationがkindへ導入できる
type parameterは256個までとする。

これはmalの型同値性を変える規則ではなく、reference compilerのresource limitである。型項のapplication、beta reduction、de Bruijn
substitution、kind substitutionは同じtransactionのbudgetを共有し、canonical nodeを構築する前にbudgetを消費する。単なるindex shiftや
kind substitutionが恒等写像になる場合は既存のDAGを共有する。

## 理由

simply typedな型項は停止しても、小さいhigher-order termから非常に大きいnormal formを作れる。特にconstructorを二回合成するaliasを
反復すると、sourceの深さと物理表現検査の前に必要な正規化量が対応しない。物理表現の上限だけでは、kindが`Type`でないconstructor
termを保護できない。

normal formを別の事前passで正確に見積もるには、beta reductionが新しいredexを作るためhigher-orderなcost transformerが必要になり、
正規化器を二重に実装することになる。実際の正規化器がallocation前に飽和budgetを消費すれば、同じ構造判断を一箇所で行える。
256 levelと65,536 stepは通常の手書きconstructorから十分離れ、既存の構文上限と物理表現上限を通る入力を扱いつつ、host stackと
一transactionの一時allocationを限定する値として採った。

## 棄却した案

- higher-kinded parameterをaffineに制限する: `Twice<F, A> :: F<F<A>>`のような有限で有用なconstructorまで拒否する。
- 正規化後にnode数だけを測る: diagnosticへ到達する前にmemoryを使い切る。
- DAG共有だけに依存する: 共有できない中間termを多数作る入力のworkを制限できない。
- timeoutやallocator failureに任せる: deterministicなdiagnosticとsource spanを返せない。
