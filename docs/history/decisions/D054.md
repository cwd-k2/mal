# D054. canonical memoryはnamed alias helperでC hostへ接続する

- Status: Accepted
- Date: 2026-09-17
- Scope: reference C host ABI v0.6

## 決定

`HostMappable(T)`と`Representable(T)`をともに満たすentry sourceのpublicなnongeneric type alias `T`に、generated headerが
`mal_T_read`と`mal_T_write`を生成する。helperはAddressとUSize indexを受け、canonical memory representationとpublic C carrierを
fieldごとに変換する。public carrier自身のlayoutはcanonical layoutとして保証しない。
require先のaliasはextern signatureが要求しない限りentry programのC surfaceへ再公開しない。

canonical layout planはLLVM memory loweringとC helperで共有する。helper生成対象のjudgmentとvisibilityはcheckerが決定し、C backendは
そのadmitted metadataを実装する。bounds、permission、initialization、lifetime、offset overflowはoperation固有contractに残す。

## 理由

D053によりmanaged ownerをmal内へ閉じ、hostとのtransportをAddressへ限定できた。一方、Address先にあるproductやsumをhostが扱うたびに
canonical offsetとtag encodingを手書きすると、layout authorityがadapterへ漏れ、target差とunaligned accessを正しく扱えない。
named alias helperなら、hostへ必要な型だけを明示的な名前で渡しつつ、layout knowledgeをcompilerに保持できる。

`HostMappable`だけではexternal opaque valueをcanonical memoryへ置けず、`Representable`だけではSymbolやmanaged memory typeをpublic
carrierへ写せない。二つのclosed judgmentの積を使うことで、新しい例外的なownership規則を追加せずに境界を定められる。

## 採らない案

- `mal_T_t *`へcastする: public C padding、canonical sum tag、unaligned access、C effective typeの規則をlayout contractへ混入させる。
- strideとfield offsetだけをmacroで公開する: host adapterが再帰変換、tag検査、active payloadの選択を再実装する。
- 任意のanonymous shapeへ汎用helperを生成する: C側の安定した名前と意図された公開surfaceを持たず、headerを構造型registryの詳細へ結合する。
- boundsとlifetimeをhelperで所有する: Addressが保持しないextent、permission、ownership authorityを共通ABIが推測することになる。

この判断はD053の「extern surfaceから到達できる型だけをheaderへ生成する」という範囲を、条件を満たすpublic named aliasまで拡張する。
managed typeを公開しない判断とABI `0x000800`は維持する。現在の規範は
[C host ABI](../../spec/c-host-abi.md#canonical-memory-access)を正とする。
