# D055. managed ownerの後継をexecution planで正規化する

- Status: Accepted
- Date: 2026-09-18
- Scope: backend非依存のexecution ownership planningとreference LLVM lowering
- Refines: D033

## 問題

現在のLLVM backendはcontrol CFGからdead localを再解析する一方、frameとregion遷移のowner move、aggregateへの保存、
closure capture、call parameterのretainを各emitterが個別に決める。この構成では、同じ責任を複数の保存先へ渡す場合の
retain順序、最後のread-only useとowner transferの違い、terminatorとframeを含むcleanupを一つの規則から検証できない。

managed aggregateもcarrier全体で一つのownerを持つわけではない。productはmanaged leafごと、sumはactive payloadの
managed leafごとに独立した責任を持つため、aggregate単位の`owned` flagだけではshareとtransferを正確に表せない。

## 決定

`execution/ownership`は、control liveness、call mode、parameter destination、frame planを入力として、managed responsibilityの
生成、use-siteの効果、終了をbackend非依存のownership planへ構成する。LLVM backendはこのplanを再推論せず、型付きの
retain、release、zero、aggregate traversalへ変換する。

ownership planはmanaged leafのresponsibility originとuse-siteの効果を区別する。次の効果はvalue固有の属性ではない。

- `Fresh`はruntime operation、managed result、またはactivationへのowned handoffからresponsibilityを受け取るoriginである。
- `Borrow`は値を観測するが、元のresponsibilityを後継へ渡さない。
- `Share`は独立して終了できるresponsibilityを一つ作り、元のresponsibilityを維持する。
- `Consume`は既存responsibilityを一つのowner successorへ移し、source carrierを失効させる。borrowed valueには適用せず、
  破棄も意味しない。
- `Drop`は後継を持たないmanaged responsibilityを終了する。source destructor、wildcard構文、Extern resourceのcloseまたはfreeを
  意味しない。

一つのresponsibility lineageは`Fresh`または`Share`から始まり、0回以上の`Consume`を経て、最後に一度だけ`Drop`されるか、
program rootからterminal boundaryの外へowned handoffされる。read-only operationの最後のuseは`Borrow`とその後の`Drop`であり、
`Consume`とはしない。reference LLVM loweringは`Share`をretain、`Drop`をrelease、addressableなsource carrierの失効をzero storeで実現する。

use-siteはclosure変換時のatom identityだけで識別しない。control変換とexecution optimizationは一つのatomを複数の実行箇所へ
置けるため、state、bindingまたはterminator、operandの役割と位置からなる構造的なidentityを使う。frame field、parameter entry、
active environmentのようなsynthetic useも同じplan内で明示する。planはmanaged useと終了点についてtotalであり、debug validatorは
authorityから期待集合を再構成して欠落と余分を検査する。

owner successorは、同じmanaged leafを保持するsinkまたはowned inputを受理するoperationに限る。同じ責任から複数のowner
successorを作る場合、先行するsuccessorを`Share`し、source order上で最後に構造的な条件を満たす一つだけを`Consume`する。
その条件は、sourceがowned responsibilityを持ち、そのuse以前の`Borrow`と`Share`が完了し、同じpathの後続でsourceが不要であり、
targetやruntime capacityによらずvalidatorがauthorityから再構成できることである。すべてのoperandを評価し、必要な`Share`を完了して
からsource carrierを失効させ、destinationの旧responsibilityと他のdead sourceを`Drop`し、destinationの更新を行う。
このtransactionalな順序により、`(x, x)`、slotの交換、sourceとdestinationが同じ遷移を特例なしに扱う。

productは各managed field、sumはactive payloadだけに同じ規則を再帰適用する。borrowed aggregateから得るfieldはborrowであり、
fieldがowner successorへescapeするときだけ`Share`する。owned aggregateの分解は選択したfieldへ責任を移し、wildcard fieldの
責任を`Drop`する。closure environmentはcapture leafの責任を持つ一つのmanaged ownerであり、closure shareではenvironmentを
一度だけretainする。environmentの最後のreleaseがcaptureを再帰的にreleaseする。

通常のnative direct callとfirst-class indirect callは、argumentとenvironmentをcall中だけborrowし、managed resultをownedで返す
共通ABIを維持する。calleeがparameterをlocal ownerとして保存する場合はshareを作る。region内遷移、`DirectSelfTail`、frame field、
returnはowner successorを明示するhandoffであり、sourceがその後不要なら`Consume`、なお必要なら`Share`を使う。native callへ
owned entryを追加する変更は、first-class ABIと別の入口を正当化する測定を伴う独立した判断とする。

last-useに唯一のowner successorがある場合の`Consume`は、このownership modelの正規形とする。これはD033が将来の最適化として
残したlast-use moveのうち、owner successorへのhandoffに限って置き換え、optional optimization techniqueには
しない。sourceを維持する必要がある場合の`Share`、後継がない場合の`Drop`を含む保守的なloweringも意味は同じだが、現在の
reference compilerは責任の不要な複製と即時破棄をownership planで正規化する。`Symbol` storageの一意性を利用した再利用のように、
移されたresponsibilityの内部storageをruntime operationが再利用する判断とborrowed temporary slot化はoptional techniqueに残す。

source semanticsはimmutable value、effect order、到達したtrap、選択したrepresentationで有効なEngram構成に必要な`Fresh` storageを
確保できない場合のfailureを観測する。ownership planに存在しない冗長な`Share`と`Drop`を仮に実行した場合のfailureを再現する必要はない。
実際に必要なruntime allocationのfailureとreference count overflowは既存のfatal resource failure規則に従う。

このplanはmal内部のmanaged valueだけを対象とする。public C ABIへmanaged carrierやeffectを公開せず、Addressのreferentとexternal
opaque valueのresource ownershipを推論しない。

## 理由

responsibilityの後継をexecution planに置くと、control liveness、call mode、frame payloadというprogram固有の事実を所有するstageで
判断が閉じる。LLVM emitterはlayoutとinstruction emissionに専念し、別backendも同じowner graphを利用できる。

`Borrow`、`Share`、`Consume`、`Drop`を分けることで、値の観測、責任の複製、責任の移譲、責任の終了が直交する。最後のuseという
一つの事実だけでread-only runtime callへ所有権を渡す誤りを避け、aggregate、branch、call、frame、returnを同じ保存則で検証できる。

## 帰結

- backend-localなmanaged liveness再解析とvalue全体の`owned` booleanをownership authorityとして使わない。
- mandatoryなowner successor graphとtarget固有のstorage再利用decisionを分離する。
- branchは相互排他的な各pathで責任保存を検査し、join前に物理的なowner identityの一致を要求しない。
- state内だけでlifetimeが閉じるborrowed temporary slotは、lenderのlivenessをlast useまで保持できる場合に限り後から導入できる。
  stateを跨ぐborrowはprovenanceとframe livenessを拡張する別の設計なしに導入しない。
- duplicate aggregate field、active sum payload、borrowed parameter return、wildcard discard、tail handoff、capturing closure return、
  self closure escape、frame environmentについてfocused testで責任保存を検査する。
