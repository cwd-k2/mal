# D061. Packed構築authorityを`Buffer<A>`として渡す

- Status: Accepted
- Date: 2026-09-19
- Scope: language、compiler、reference LLVM backend

## 問題

`pack`と`edit`は従来、builderをcaptureした`new`、`get`、`put`の三つのfunction valueをcallbackへ渡していた。この表現では
一つのscoped mutable authorityが三つの独立したclosureに見え、helperは同じbuilder由来であることを型に表せない。compilerも
function dispatch、environment compact化、builder provenanceの復元を必要とし、素直なsource codeの性能が間接表現に左右された。

一方、callback外へbuilderを返せないことは既存のscope規則で成立している。この制約のためにoperationごとのfunction valueを作る
必要はない。

## 決定

`pack<A>`と`edit<A>`はcallbackへ一個の`Buffer<A>`を渡す。`Buffer<A>`にはsource-level constructorがなく、`new`、`get`、`put`は
Buffer operandを取るpredefined operationである。receiver-first applicationにより`buffer.new(value)`、`buffer.get(index)`、
`buffer.put(index, value)`と書け、通常のUFCS形でも同じoperationを指す。

`Buffer<A>`は`Representable(A)`の場合だけwell-formedで、値自身はRepresentableでもHostMappableでもない。helper、nested closure、
recursive callへ渡せるが、callbackの正常完了後には到達できない。`pack`と`edit`の結果、copy-on-write、評価順、未検査preconditionは
従来の`Packed` contractを維持する。

compilerは`Buffer` operationをfunction applicationへ変換せず、element型を持つbuilder operationとしてcore以降へ渡す。LLVM backendは
runtimeが保証するcanonical alignmentでPacked storageへ直接accessし、editの最初の変更だけlazy preparationを行う。

## Authorityからの導出

sourceが観測するauthorityはoperationごとの呼出し能力ではなく、callback期間中の一つのbuilderである。三つのfunction valueは
旧loweringのmechanismであり、言語の意味ではない。従ってbuilderを直接表す型を置き、operationをそのoperandから型付けする方が
scope、mutationの順序、element型を一箇所から導ける。

Packed backing storageはruntimeがcanonical alignmentを保証するため、LLVM accessも同じalignmentを使える。外部storageであるRegionの
exact accessにはこの保証がなく、`align 1`を維持する。

## 帰結

- helperは三つのfunction型ではなく一個の`Buffer<A>`を受け取る。
- closure conversion、ownership、LLVM backendからPacked intrinsic capability専用表現を削除する。
- `pack`での初期構築と`edit`での変更を同じsource-level operationで記述し、両者を同じコーパスで比較できる。
- D059とD060のcopy-on-writeを遅延する意味上の判断は維持するが、capability target解析とcompact environmentによるmechanismは置き換える。
