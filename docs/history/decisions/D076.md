# D076. process argumentを`Symbol`のBufferで渡す

- Status: Accepted
- Date: 2026-09-25
- Scope: language (entry point), C host ABI, and reference compiler
- Supersedes: [D073](D073.md)

## 問題

[D073](D073.md)は`main`のargumentを`(Address, USize)`のBufferにした。Addressはhostのstorageを指すcapabilityで、`main`のreturnまで
という有効期間を持つ借用だった。argumentは環境から入る値であり、programが行うのはflagやsubcommandの判定、値の分解、数値のparse、
別の文字列との連結といったbyte列の加工である。これらは`Symbol`の操作であり、Addressのままでは各programが
`*from<UInt8>(address, 0usize, length)`でSymbolへ取り込む必要があった。

`Buffer`が`Symbol`を要素に持てるようになった（[D075](D075.md)）ため、entryもSymbolにできる。

## 決定

argument-aware entryの型を`Buffer<Symbol>`にする。C shimが起動時に`argv + 1`の各C stringを、終端NULを除いてcopyしたSymbolを持つ
Bufferを作り、rootのreturn後に解放する。argumentはmal-ownedな値であり、有効期間の制限を持たない。`Unit -> Int32`とこの型
以外の`main`はcompile-time errorのままである。

argumentをhostへ渡すときは、他のSymbolと同じくhost storageへcopyする。examplesではこの変換を、host側の`.mal` moduleに置く
一つの関数（`readableBytes`など）で書いた。

## 理由

- 環境から入るデータはmal-ownedな値として取り込むのが、[EngramとExtern](../../spec/engrams.md)の分担である。借用のAddressは、寿命が
  暗黙に限られるextern側のcapabilityで、この分担から外れていた。
- SymbolからhostへのcopyはSymbol一般の境界であり、argvに限らない。パスを別の文字列と連結した結果も同じ変換を要する。
  argvだけをAddressで渡しても、変換の必要は減らない。
- 主要な言語（Rust、Go、Pythonなど）はargvを文字列の列として渡す。C stringの`char **`が例外である。

## 採らなかった判断の訂正

同日、examplesの使われ方から`Buffer<(Address, USize)>`の維持を判断したが、これは撤回する。根拠にした「argumentのAddressを
そのままfile openのexternへ渡す例が4本中2本ある」は、hostの実装を読むと成り立たなかった。二つのhostは受け取ったbyte範囲を
自前で終端NULのbufferへcopyしており（NULの含有も検査する）、argvのC stringが終端NULであることに依存していなかった。
また、現在ある例だけから一般の使い方を判断したこと自体が誤りだった。

## 帰結

- 失うのは、argumentを加工せずhostへ渡すだけのprogramでの変換の記述と、その一回のcopyである。
- 引数を他のprocessへ転送するhostが必要とするC stringの配列は、hostが自分で組み立てる。
- examplesの`brainfuck-llvm`と`json-query`では取り込みの一行が消え、`mini-database`と`recoverable-file`ではSymbolをhostの
  byte範囲へ書く関数が増えた。
