# D062. edit storageをcallback前に一度prepareする

- Status: Accepted
- Date: 2026-09-19
- Scope: core loweringとchecked-in C runtime

## 問題

`edit`のsourceとresultは独立したimmutable valueである一方、仕様はwritable storageの確立をcallback開始前と最初の変更時のどちらも
許している。D060は後者だけを仕様上の要請として扱ったため、選択可能なruntime policyを過度に狭めていた。また、各`put`で
editable状態を検査すると、構築後に編集して走査する通常のloopへ不要な分岐が残る。

## 決定

core loweringはedit builderを作った直後、callbackを呼ぶ前に`Prepare`を一度置く。source valueの最後のresponsibilityはbuilder作成時に
処理済みであるため、runtime ownerが一意でview全体を指す場合はstorageをその場で再利用する。それ以外はこの時点でcopyする。
`put`はprepared storageへ直接storeし、editable状態を再検査しない。

no-op editでownerを共有するかcopyするかは仕様上のimplementation detailであり、このimplementationはcallback内の一様なaccessを選ぶ。

## Authorityからの導出

仕様はsource/resultの独立性、operation順序、allocation failureを所有し、prepare時点とstorage再利用を実装へ委ねる。coreはcallbackとの
evaluation boundaryを所有し、execution ownershipはsource responsibilityの最終useを所有する。runtimeはowner uniquenessとview範囲を
検査する。従って、これらの既存factが揃った境界で一度prepareする判断は新しい意味論を導入しない。

## 帰結

- edit callback内の`get`と`put`は同じactive dataを使う。
- no-op editもsharedまたはpartial viewならcopyし得る。
- growthだけがprepare後のactive dataを移動し得る。
- sourceを後から観測するprogramでsourceの値は変化しない。
