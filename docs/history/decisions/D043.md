# D043. receiver-first application（UFCS）を通常のapplicationへ消去する

- Status: Accepted
- Date: 2026-09-12
- Scope: mal v0.5 source language

## 決定

calleeがvalue nameであるapplicationには、第一引数をreceiverとして先に書く
`receiver.function(arguments)`を認める。この形は`function(receiver, arguments)`へ消去し、
通常のlexical name resolution、function applicationの型規則、value-firstの評価順を使う。

`.§、value name、parenthesized argument listは全体で一つのapplication suffixである。
`receiver.function`だけの形は認めず、field、property、method value、bound functionを導入しない。
receiverの型からmember、extension、適合するfunctionを探索せず、callee名はsource位置のlexical scopeだけから解決する。

## 理由

通常callのnestingはdata transformationの順序と逆向きに深くなる。第一引数を処理の主題として左に保つ表記により、
複数引数を取るdomain operationも左から右へchainできる。dot callは既存言語で広く使われる形であり、
初見の利用者がreceiverとoperationの関係を認識しやすい。

一方、type-directed lookupやmember valueを加えると、同じoperationに名前解決、優先順位、dispatch、暗黙closureという
独立contractが生じる。receiver-first形を通常のapplicationへの局所的な変換に限定すれば、表面の読みやすさを加えても
core calculus、型、runtime representation、host contractは増えない。

Malでは`f(a, b)`が`f((a, b))`、`(a, b)[f]`と同じapplicationであるため、
`a.f(b)`もこの既存関係の別表記として完全に説明できる。
