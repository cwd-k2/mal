# D041. 実行計画をLLVM IR、runtimeとpublic interfaceをCに分ける

- Status: Accepted
- Date: 2026-09-10
- Scope: reference compiler execution backend

## 決定

解析済みMal programに固有のfunction body、control flow、call、frame、typed data operationとownership operationはLLVM IRとして
生成する。allocation、reference count、control storage growth、Symbolなどprogram非依存のmechanismはC runtimeに置く。

host-visible type、extern adapter、terminal return、process entryはgenerated C headerとC shimに残す。LLVM moduleとの内部bridgeは
opaque pointerとresult out-pointerを基本とし、LLVM representationとcalling conventionをpublic C ABIへ公開しない。scalarを
signatureで直接渡す場合はC declarationとLLVM parameter attributeを同じtarget-aware ABI planから生成する。

non-tail recursionのcontinuationは明示的なgrowable storageに残す。LLVMにはactivation-local valueのSSA化、register allocation、
state transition、known callの最適化を委ねるが、unboundedなcontinuation storage policyは委ねない。

target toolchainはpinned Clang/LLVM、runtimeとshimとhost adapterはC11に限定する。GCCその他のC compilerとの互換性を
reference compilerの設計条件にせず、ambient `CC`によるcompiler差し替えはbackend移行時に廃止する。

完全な責務と検証境界は[実行backendの責務境界](../../implementation/execution-backend.md)を正とする。

## 理由

生成Cのcontrol frame、dispatcher、resumeはprogram固有のmachineをC objectとstatementへ符号化しており、LLVM IRのCFG、SSA、typed
memory operationへ直接対応する。controlだけをC function境界で切り出すとstate間のvalueとowner transferがmaterializeされ、LLVMに
移す利点を失うため、generated body全体を同じoptimization unitへ置く。

storageと汎用data structureはprogramごとの差が小さく、Cで実装した方がlifetimeとfailure contractを一箇所で管理できる。public
interfaceもCに残せば、host authorへLLVM toolchain、IR type、internal closureやframe ABIを要求せず、既存C host ABIを維持できる。

## 採らない案

- 通常のrecursive LLVM callへ全面的に戻す: non-tail recursionでnative stackがMal call depthに比例する。
- control stateだけをLLVM、state bodyをC functionにする: SSA、inlining、register lifetime、typed owner moveをcall境界で失う。
- runtimeもLLVM IRで生成する: program非依存のmechanismをbackend emitterへ複製し、Cでreviewできる実装を失う。
- LLVM coroutine intrinsicへ写す: external resumeを必要とせず、recursive frame allocationも消えず、release間compatibilityを前提にできない。
- public C aggregate ABIをLLVM frontendで直接再現する: target別ABI loweringをreference compilerへ追加する。
- GCCを含む任意C compilerをruntimeまたはhost interfaceに認める: LLVM moduleと異なるtoolchainのtarget、ABI、optionを追加で検証する必要がある。

## 位置づけ

[D002](D002.md)が記録したRust compilerは維持する。D041は最初のC execution backendをLLVM backendへ置き換え、
[D012](D012.md)と[D040](D040.md)のC host adapter判断を置き換えない。移行中だけ旧C backendをdifferential testのoracleとして
残し、LLVM経路が全admission範囲を満たした時点で`emit-c`とともに撤去する。
