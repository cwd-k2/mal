# D039. external operationを通常のfunction valueとして導入する

- Status: Accepted
- Date: 2026-09-09
- Scope: mal v0.5 source language

## 決定

`extern` declarationは通常のtop-level function valueを導入する。呼び出しには通常のapplicationを使い、
call siteへ`extern`を重ねて書かない。external functionは値としてbindingし、引数またはresultとして受け渡せる。

```mal
extern print :: Symbol -> Unit;

run :: (Symbol -> Unit) -> Unit := \(output) { output("hello") };
main :: Unit -> Unit := \() { run(print) };
```

function valueの参照と受け渡しはhost operationを実行しない。applicationしたときに宣言されたoperationを一度実行し、
そのparameterとresultへextern boundary transportを適用する。external nameも通常のlexical shadowingに従う。

reference compilerはexternal declarationを、host operationを本体に持つcapture-freeなtop-level functionへlowerできる。
既知のcalleeに対するdirect call化は観測可能な評価順と境界transportを保存する最適化である。

## 理由

malはeffect systemを持たず、通常のfunctionも内部でexternal operationを呼び得る。このためcall siteの`extern`は
purity、作用、authority crossingの推移的な保証にはならず、宣言ですでに決まった分類を直接callごとに再記述していた。
宣言されたfunction identityからhost contractを選べば、通常のvariable、shadowing、application規則だけで同じ境界を表せる。

authorityの移動はfunction valueの取得ではなくapplicationのparameterとresultで起きる。function value自体はmalが
identityとlifetimeを支配するEngramであり、external signatureを通るcallbackではない。したがってfunction型をextern
parameterまたはresultに含めない既存制約とも両立する。

専用call syntaxとexternal name専用の参照規則を削除するとlanguage surfaceとname-resolution contractが減る。
一方、host contract、transportable type、ABI、trusted adapterの責務は宣言に残るため、境界modelを暗黙化しない。

## 採らない案

- bare callだけを許可し、external operationをfirst-class valueにしない: call位置だけに有効な名前という例外が残り、
  通常のapplicationとの違いを別途規定する必要がある。
- call siteの`extern`をeffect markerとして維持する: wrapper functionのcallではmarkerが消えるため、推移的なeffect規則に
  ならない。必要なら将来、external operationだけでなく作用全体を扱うeffect systemとして検討する。
- external nameによるlocal shadowingを禁止する: 通常のlexical scopeに例外を加え、別名を選べば回避できる衝突を
  言語全体の制約にする。

[実行意味論](../../spec/execution.md)が定める。authorityの分類は
[EngramとExternのauthority](../../design/authority.md)、minimalityの判定は
