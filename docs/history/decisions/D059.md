# D059. Packed builderのstable data accessをLLVM techniqueとして選択する

- Status: Accepted
- Date: 2026-09-19
- Scope: reference LLVM backendとchecked-in C runtime

## 問題

`pack`の`get`と`put`は同じbuilderから作られても独立したfunction valueとしてproduct、call、recursive controlを通過する。
LLVM backendが各capability environmentからbuilderのactive data pointerを毎回読むと、element storeがopaqueなbuilder metadataと
aliasし得るものとして扱われ、fixed-size mutable workloadでもloadの保持、inlining、vectorizationが阻害される。

仕様が定めるのはbuilder operationの順序と観測可能なeffectである。contiguous representationは意味論ではなく、data pointerを
変更し得るoperationはchecked-in runtimeのgrowthとcopy-on-write mechanismによって決まる。この区別を失ってdata pointerの安定性を
executionの意味論的factにすると、runtime表現の判断を誤ったauthorityへ置くことになる。

## 決定

`backend/llvm/optimization/packed_data`を任意のLLVM techniqueとする。application graphとcontrol continuationはadmitted execution
planから読み、runtime mechanism上data pointerを変更し得るcapability applicationを求める。`New`、`NewUnique`、editの`Put`と、
それらへ到達するinternal functionを固定点で分類する。function内のcontinuationだけでなく、すべてのcallerでcall return後に到達し得る
executionも固定点で伝播する。

現在のdecisionはbuilder identityを推測せず、対象application以後にどのPacked builderについても上記operationへ到達しない場合だけ、
`Get`とunique builderの`PutUnique`をstable direct accessへ選択する。異なるbuilder、同じelement型、nested call、recursive return contextを
統合しない。空のLLVM technique集合ではdecisionを一つも作らず、通常のcapability callだけで同じprogramを実行する。

選択済みapplicationでは、runtimeがbuilder内のdata slot addressを返し、LLVM emissionがそのslotにinvariant scopeを開始してdata
pointerを読む。builder structのoffset、field順、C型をLLVM backendへ複製しない。

## Authorityからの導出

言語仕様は`new`が末尾へ追加し、`get`が現在値を観測し、`put`が現在値を置換し、先行operationの結果を後続operationが観測することを
所有する。一方、growth時の再配置、editのcopy-on-write、data slotはruntimeが所有する。application targetと到達可能なcontrolは
execution planが所有する。

したがって、execution planを変更せず、runtime表現で無効化operationが後続しないsiteだけを直接accessへ変える判断はLLVM backendの
authorityに属する。これは言語上のbuilder identityやdata pointer stabilityを追加するsemantic factではなく、複数authorityの既存factを
読むemission decisionである。

## 帰結

- `Get`後にreachableな`New`または`NewUnique`がある場合は直接accessにしない。
- editの`Put`前後はcopy-on-writeを跨ぎ得るため直接accessにしない。
- `PutUnique`はchecked-in runtimeでdata pointerを変更しないが、後続のgrowthがない場合にだけ直接accessにする。
- runtimeがbuilder layoutを所有し、backendはdata slot accessorだけを利用する。
- exact validatorは有効なtechnique集合からdecision集合を再構成する。
- baseline、単独適用、productionのIR shapeとobservable resultを検証する。
