# D059. Packed builder dataの安定区間をexecutionで証明する

- Status: Accepted
- Date: 2026-09-19
- Scope: backend非依存のPacked execution planningとreference LLVM lowering

## 問題

`pack`の`get`と`put`は同じbuilderから作られても独立したfunction valueとしてproduct、call、recursive controlを通過する。
LLVM backendが各capability environmentからbuilderのactive data pointerを毎回読むと、element storeがopaqueなbuilder metadataと
aliasし得るものとして扱われ、fixed-size mutable workloadでもloadの保持、inlining、vectorizationが阻害される。

environment pointerの一致やfunction typeだけでは同じbuilderを証明できない。また`New`と`NewUnique`はgrowthによりdata pointerを
変更し、editの`Put`はcopy-on-writeによりownerとdataを変更し得る。backendがruntime layoutから安定性を推測してはならない。

## 決定

`execution/packed`はapplication graphとcontrol continuationを入力に、builder metadataを変更し得るcapability applicationを求める。
`New`、`NewUnique`、editの`Put`と、それらへ到達するinternal functionを固定点で分類する。function内のcontinuationだけでなく、
すべてのcallerでcall return後に到達し得るexecutionも固定点で伝播する。

現在のplanはbuilder identityを推測せず、対象application以後にどのPacked builderについてもmetadata mutationへ到達しない場合だけ、
unique `Get`と`PutUnique`へstable data access factを付与する。この保守性により異なるbuilder、同じelement型、nested call、recursive
return contextを統合しない。builderごとのprovenanceで適用範囲を広げる場合も、このfactの意味は変更しない。

LLVM backendはfactを持つapplicationだけを直接data accessへ変換する。runtimeがbuilder内のdata slot addressを返し、backendは
そのslotにinvariant scopeを開始してdata pointerを読む。builder structのoffset、field順、C型をLLVM backendへ複製しない。
factを持たないapplicationは従来のcapability callを維持する。

## 理由

data pointerの安定性は言語の型やclosure representationではなく、将来到達し得るeffectを含むexecution上の事実である。
executionで証明すれば、backendはtarget表現を選ぶだけで済み、growthやcopy-on-writeを誤って跨がない。

program-wideにmutation不在を要求する初期規則は適用範囲を狭めるが、builder identityを持たない段階で異なるbuilderを統合するより安全で
ある。011と063のように構築完了後だけmutable workspaceを使うprogramにはこの規則だけで適用できる。

## 帰結

- `Get`後にreachableな`New`または`NewUnique`がある場合はstable accessにしない。
- editの`Put`前後はcopy-on-writeを跨ぐためstable accessにしない。
- `PutUnique`はdata pointerを変更しないが、後続のgrowthがない場合にだけstable accessにする。
- runtimeがbuilder layoutを所有し、backendはdata slot accessorだけを利用する。
- IR shapeのtestはstable pathがdata slotとdirect element accessを持つことを検査し、実行testは同じobservable resultを確認する。
