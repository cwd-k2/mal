# D075. Buffer elementをRepresentableからStorableへ広げる

- Status: Accepted
- Date: 2026-09-25
- Scope: language, compiler, reference LLVM backend and C runtime

## 問題

`Buffer<A>`は`Representable(A)`のときだけwell-formedだった。この条件はC hostとのcopyのためのcanonical layoutを表すが、
Bufferが要素を保持できることの条件にもなっていたため、`Symbol`はBufferの要素になれなかった。`Symbol`は`Int64`などと並ぶ
mal-ownedな値であり、`HashMap<Int64, Symbol>`のようなuser-land collectionを`Buffer<Symbol>`で書けず、
`Buffer<UInt8>`と`(offset, length)`の組で代用するとEngramとしての`Symbol`を使えない。

## 決定

`Storable(A)`を導入し、`Buffer<A>`は`Storable(A)`のときだけwell-formedとする。storableな型は`Unit`、numeric scalar、`Address`、
`ByteSize`、`USize`、`Symbol`、およびそれらだけからなるproductと二項以上のsumである。`Buffer`、function、external opaque type、
empty sumはstorableでない。`Representable(A)`は`Storable(A)`のうち`Symbol`を含まない型として残り、`from<A>`、`buffer.into`、
canonical memory helperの要素を決める。型parameterはrepresentableと仮定できないので、generic本体は型parameterの要素へ
`from`と`into`を使えない。

`Symbol`を含む要素はcanonical layoutを持たないため、runtime valueのlayoutでBuffer storageへ置く。runtimeはBufferが書く要素ごとに
一つのreferenceを取り、要素の上書きとBufferの破棄で手放す。`get`は取り出した値をretainして返す。Buffer operandは
execution ownershipでこれまでどおりBorrowであり、ownership解析は変えない。

範囲外の`get`と`put`は従来どおり未検査preconditionである。managed要素でも、実行結果を保証しないという規則は変えない。

## 理由

Bufferがmal-ownedなら、mal-ownedなimmutable値は要素にできるべきである。`Buffer`とfunctionだけを除けば、Buffer storageから別の
BufferやclosureへのedgeがなくEngramのownership graphは非循環のまま残り、referenceの管理は`Symbol`のbyte ownerだけで済む。
要素のaliasが後の変更を観測することもない。

## 採らない案

- `Buffer<Buffer<T>>`を許す: 要素の`get`がaliasを返し、同じ内側のBufferを複数のindexに置くと一方の変更が他方から見える。
  可変な二次元配列が必要なら、一つの`Buffer<T>`とstrideで表せる。
- `Buffer<Function>`を許す: Bufferを自分自身のcaptureとして持つclosureを格納でき、参照カウントでは回収できない循環を作れる。
- 全要素をruntime value layoutで格納する: sumのtag幅とBoolのstorage幅がcanonical layoutと異なり、`from`と`into`が要素ごとの
  変換を要する。canonical layoutを持つ要素は従来のstorageとcopyを保つ。
- `get`をborrowとして返す: Bufferは共有mutableであり、後続の`put`が要素を手放すとborrowがdanglingになる。
- 範囲外アクセスの検査をmanaged要素だけに課す: 型によってpreconditionの意味が変わり、言語が保証する範囲が広がる。

## 帰結

- `memory.md`は`Storable`と`Representable`を分け、[generics](../../spec/generics.md#requirements)のrequirementは`Storable`になる。
- `buffer.into`は`Symbol`を含む要素と型parameter要素を型検査で拒否する。
- C runtimeは`mal_runtime_buffer_make_managed`で要素のretainとreleaseのcallbackを受け取り、managed要素のBufferだけが
  callbackを持つ拡張objectと専用の`new`、`fill`、`copy`を使う。canonical要素のBufferのobject、確保、命令列は変えない。
  すべてのBufferにcallbackの領域と判定を置くと、Callgrindで`new`が1要素あたり約4命令、小さなBufferの生成が約3%増えた。
- `main :: Buffer<(Address, USize)> -> Int32`は変えない。`Buffer<Symbol>`へ変える判断は[D076](D076.md)で行う。
