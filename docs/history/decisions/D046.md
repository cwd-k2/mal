# D046: canonical typeの物理表現上限

Status: Accepted (2026-09-13)

## 決定

reference compilerはcanonical typeが必要とする物理storage componentを型検査で見積もり、65,536を超える型をsource span付き
diagnosticで拒否する。productは全fieldを加算し、sumはtagと最大variant、functionはclosure carrierとparameter/resultを判定する。

これはreference compilerのresource limitであり、malの型同値性、実行時trap、target固有のbyte layoutを変更しない。

## 理由

共有DAGのnode数と値の物理sizeは同じではない。`T(n) = (T(n-1), T(n-1))`は型nodeを共有できても、product値には両fieldの
storageが必要であり、LLVM type、construction、copy、owner operationも最終的に全fieldを扱う。反対に
`S(n) = [S(n-1), S(n-1)]`はactive variant一つのpayload regionを使うため、物理sizeはdepthに対して線形である。

backendが巨大な文字列やoperation列を構成してからhost allocation failureへ至るより、target非依存に判定できる最初の
authorityである型検査が拒否する。65,536 componentは通常の手書きaggregateから十分離れ、debug buildでも拒否判定前の
生成量を限定できる値として採った。target固有のbyte overflowは引き続きbackend layoutが検査する。

## 棄却した案

- canonical DAG node数だけを制限する: 小さいproduct DAGから指数的に大きい実値を作れる。
- productとsumを同じく全辺加算する: active payloadを一つしか持たないsumを誤って指数的と判定する。
- backendのchecked arithmeticだけに任せる: machine word overflowより前に巨大なIR文字列とfield operationが生成される。
