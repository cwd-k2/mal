# D064. non-growing Buffer helperのactive data引数をnoaliasにする

- Status: Accepted
- Date: 2026-09-19
- Scope: reference LLVM backend

## 問題

edit callbackがimmutable `Packed<A>`を読みながら`Buffer<A>`を更新しても、LLVMはBufferへのstoreがPackedのloadを変更し得ると判断する。
011のDP loopではjobごとに一定なdurationとrewardが反復ごとに再loadされ、sourceに現れる不変性が生成codeへ残らなかった。

PackedとBufferのelement accessを恒久的な別TBAA typeにする案では、freeze後のPacked resultが直前のBufferと同じstorageを読む事実に
反する。非aliasなのはcallback中の観測可能なimmutable valueとmutable Bufferであり、storageの全lifetimeではない。

## 決定

D063が選ぶnon-growing internal functionは、source parameterに加えてactive data pointerを一つ受け取り、そのpointer引数へLLVM
`noalias`を付ける。entryでsource parameter内の唯一のBuffer leafをこの引数から再構成し、`get`と`put`はそのprovenanceを使う。
契約はfunction invocationの間だけ成立し、freeze後へ延長しない。

一つのparameterにBuffer leafが複数あるfunctionは通常ABIへ残す。同じBufferを二度渡せるため、個々のleafを互いに`noalias`とは
みなせない。builder data slot、runtime C access、Packed index、Regionには新しいmetadataを付けない。

## Authorityからの導出

`pack`のBuffer storageは新規であり、callback中にPacked viewを作れない。`edit`はcallback前にprepareされ、source、slice、Symbol、
captureなど同じownerを観測できるimmutable viewが残る場合、runtimeのreference countにより別storageへcopyする。storageを再利用する
のは他のimmutable viewが存在しない場合だけである。従ってhelper invocation中にBufferが変更するlocationは、別のpointerから観測する
Packed locationと重ならない。

この保証はscoped builder semantics、D062のprepare境界、runtime owner policyから導く。allocator freshnessや一般のpointerを
noaliasとする規則ではない。

## 帰結

- Packed loadは同じhelper内のBuffer storeを跨いで保持できる。
- callback終了後のPacked resultは同じstorageを正しく観測する。
- 複数Buffer parameterとgrowth可能なhelperは通常ABIを維持する。
- shared sourceをcallback内で読むnative regressionをbaselineとproductionで検査する。
