# D057. aggregate ownerが包含するlocal aliasはborrowする

- Status: Accepted
- Date: 2026-09-18
- Scope: backend非依存のexecution ownership planning
- Refines: D055

## 問題

managed aggregateをbindingへ保持したままpatternでfieldを取り出すと、従来のownership planはaggregateのmanaged leafと
field bindingの双方へ独立したresponsibilityを与えていた。fieldが観測にしか使われず、aggregate ownerがfieldの全lifetimeを
包含する場合にも`Share`と`Drop`が発生し、意味が等しい直接parameter patternとの間に実行コストの差が生じる。

backendで隣接するretainとreleaseを相殺しても、branch、control frame、再構成を跨ぐlifetime authorityは復元できない。

## 決定

`execution/ownership/borrow`は`Atom(binding)`をpatternへ写すaliasと、元のsumをarm内でも保持するcase payloadについて、managed
leaf bindingから元のaggregate bindingへのprovenanceを構成する。owner successorを持たずにdiscardされる純粋なproductとsumは、
構成要素をlenderとするborrowed resultにする。transparentな`Atom`とlocal `Jump` inputを逆向きに辿り、result blockが作る
administrative state境界でも同じ判断を保つ。

control state入口でborrowed bindingがliveなら全lenderもliveであることを確認し、state内のbackward livenessではborrowed bindingの
生存がlenderの生存を要求する。条件を満たすbindingはowner successorではなく`Borrow` destinationへ格納する。

borrowed aliasをframeへ保存する場合、frameはcarrierだけを運びresponsibilityを持たない。同じframeに残るlender fieldがstorage
lifetimeを支配する。aliasから生きたproduct、sum、closure environment、returnその他のowner successorを作るuseは通常どおり
`Share`し、alias自体を`Consume`または`Drop`しない。closure生成はenvironment allocationと独立したlifetimeを持つため、resultを
discardする場合もproductやsumの純粋な構成と同一視しない。

候補ごとにCFGを再走査しない。通常livenessからprovenance候補を集め、state live fieldを一度走査してframe境界を検証した後、
lender dependencyを閉じたownership livenessを再構成する。

## 理由

aggregate ownerがstorage lifetimeのauthorityであり、観測用field bindingはそのauthorityを複製しない。provenanceとcontrol
livenessを持つexecution stageなら、source spelling、target、runtime reference countに依存せずこの関係を判断できる。

product再構成やclosure captureのようにaliasが新しい独立ownerへescapeする場合は`Share`が残る。したがってborrowは必要な
responsibilityを省略する最適化ではなく、責任を持たないaliasをそのまま表す正規形である。

## 帰結

- aggregateを名前で保持してから分解する表記と、parameter patternで直接分解する表記は同じowner graphへ近づく。
- sum ownerをarm内で保持するcase payloadにも同じ包含規則を適用する。
- frame layoutはborrowed carrierを保持できるが、retain、release、consumeの対象にしない。
- lenderがaliasより先に終了するpathが一つでもある候補は従来どおりowned bindingにする。
- 生きたproduct、sum、closure environmentはowner successorであり、borrowed aliasを保存するときだけ新しいresponsibilityを作る。
- discardされる純粋なproductとsumは複数の構成要素をlenderにできる。closure生成のallocationとenvironment ownershipは維持する。
- focused ownership testとmanaged frameの実行testでplanとruntime lifetimeの双方を検証する。
